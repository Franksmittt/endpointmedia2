Cursor Blueprint: Next.js 16 Technical SEO Architecture and Indexing Resolution
The modern JavaScript web framework ecosystem introduces profound complexities for search engine crawling, rendering, and indexing pipelines. When enterprise architectures leverage the Next.js App Router—specifically transitioning through versions 15 and 16—developers frequently encounter severe indexing bottlenecks. These bottlenecks most notably manifest within Google Search Console as "Discovered - currently not indexed" and "Crawled - currently not indexed" anomalies. These critical errors represent fundamental failures in the communication protocol between the application's routing infrastructure, its rendering strategy, and Googlebot's Web Rendering Service (WRS).1 The resolution of these anomalies requires bypassing generic search engine optimization directives and implementing strict, framework-specific architectural modifications.
The "Discovered - currently not indexed" status indicates a fundamental crawl budget deficit or a routing trap.1 In these scenarios, Googlebot has identified the Uniform Resource Locator (URL)—often through an XML sitemap or an internal HTML link—but the crawling scheduling algorithms have actively deprioritized the fetch request.1 This algorithmic deprioritization is overwhelmingly caused by excessive 308 Permanent Redirect chains, invisible proxy routing barriers, or server latency signatures that signal to the crawler that the domain is structurally unstable or excessively resource-intensive to map.3 Search engines operate on strict computational budgets; if a Next.js application forces the crawler through convoluted routing logic, the engine simply drops the URL from the active crawl queue.
Conversely, the "Crawled - currently not indexed" status highlights a catastrophic failure in the rendering or canonicalization pipeline.1 In this state, Googlebot has successfully fetched the document payload over the network, but the indexing engine has actively rejected the content upon evaluation.1 Within Next.js App Router implementations, this rejection is frequently driven by client-side rendering (CSR) hydration delays that mask the raw Hypertext Markup Language (HTML) content, relative canonical URL mismatches that dilute link equity, or unintentional noindex directives injected dynamically at the edge network boundary.1
To completely resolve these bottlenecks in Next.js 15 and 16 environments, the application architecture must be systematically hardened at the configuration level. This requires absolute precision in route normalization, static metadata generation, server-side component streaming, and network-level proxy interception. The subsequent technical blueprint provides the exact file structures, configuration objects, and validation engines required to eliminate Googlebot friction and enforce pristine indexing pathways.
The Web Rendering Service and JavaScript Execution Costs
To architect a highly indexable Next.js application, one must first deconstruct the mechanics of Googlebot's two-phase indexing process.2 Search engines do not experience modern single-page applications or React-based frameworks in the same manner as a standard web browser. When Googlebot first encounters a URL, it executes an initial crawl phase designed exclusively to parse the raw, immediately available HTML payload.2 This initial pass operates without executing JavaScript. If the essential content, canonical tags, and metadata are present within this raw HTML, the page is rapidly processed and queued for indexing.1
However, if the application relies heavily on client-side JavaScript to fetch data or render the Document Object Model (DOM), the initial HTML payload delivered to the crawler is often nothing more than a hollow skeleton, such as an empty <div id="root"></div> tag alongside a script bundle.2 Recognizing that the page requires programmatic assembly, Googlebot pushes the URL into a deferred rendering queue.2 This deferred queue utilizes the Web Rendering Service, a headless Chromium instance tasked with downloading the JavaScript bundles, executing the React tree, and hydrating the DOM to reveal the final content.1
This deferral introduces massive indexing vulnerabilities. The Web Rendering Service is computationally expensive and heavily rate-limited. When a Next.js application suffers from hydration lag—where heavy client-side JavaScript struggles to attach event listeners to server-rendered HTML or fetch missing data—it causes severe CPU spikes.1 If this execution locks the main thread or exceeds the crawler's allocated rendering time, Googlebot will simply abandon the render before the content becomes fully interactive or visible.1 The result is a "ghost page" where Google only indexes the skeleton state, or worse, abandons the indexing attempt entirely, flagging the page as "Crawled - currently not indexed".1 Consequently, minimizing reliance on the deferred rendering phase by serving fully populated HTML on the initial request is the paramount objective of technical Next.js optimization.
Configuration Protocol: Routing and Trailing Slash Normalization
The Next.js framework's internal handling of trailing slashes is a primary vector for crawl budget exhaustion and redirect loops, directly causing "Discovered - currently not indexed" anomalies. The trailingSlash configuration parameter within the next.config.js file dictates whether the routing engine resolves paths with or without a terminal slash. If trailingSlash: true is declared, Next.js natively intercepts all incoming requests to non-slashed URLs and issues an HTTP 308 Permanent Redirect to their slashed counterparts.6 For example, a request to /about is forcefully redirected to /about/.6
The architectural crisis occurs when the application's dynamic sitemap.ts generates URLs that contradict this central next.config.js enforcement.3 If the programmatic sitemap broadcasts https://example.com/about, but the server configuration enforces trailingSlash: true, Googlebot is force-fed a continuously invalid list of URLs.3 Upon processing the XML sitemap, the crawler initiates highly concurrent fetches for every declared URL. Instead of receiving HTTP 200 OK responses, the crawler is immediately intercepted by hundreds or thousands of 308 Permanent Redirects pointing to the slashed versions.3 This continuous redirect friction forces Googlebot to discard the original URLs, throwing the "Discovered - currently not indexed" error as the scheduling algorithm refuses to squander its computational budget on misaligned internal routing.1
Furthermore, recent updates in Next.js 14, 15, and 16 automatically normalize canonical metadata URLs by stripping or appending slashes based entirely on these internal API configurations.8 This framework-level intervention can result in the <link rel="canonical"> tag conflicting with the actual requested URL, creating duplicate content signals that further confuse search engine algorithms.8 When trailingSlash: true is set, metadata URLs returned by the generateMetadata function will have a trailing slash appended automatically, overriding manual string definitions.9
To establish a flawless architecture and preserve crawl budget, the system must enforce strict uniformity. The safest and most performant default for modern Next.js enterprise deployments is to enforce trailingSlash: false to prevent unwarranted 308 generation, while concurrently utilizing the skipTrailingSlashRedirect parameter.10 This combination prevents the framework from hijacking the routing layer, allowing the developer to manually maintain control over specific path normalizations, particularly during large-scale site migrations where legacy trailing slashes must be preserved via proxy rewrites rather than global redirects.11

	Metadata API and Canonical Link Resolution Imperatives
Canonical URLs serve as strict directives instructing search engine indexing algorithms on how to consolidate duplicate or near-duplicate content signals into a single, authoritative master URL.7 Within the Next.js App Router architecture, canonicalization is systematically managed via the framework's native Metadata API.15 A critical, widespread architectural failure point arises when developers omit the metadataBase property within the root layout while simultaneously supplying relative paths to the alternates.canonical object in child routes.5
When the metadataBase property is absent, relative URLs—such as defining canonical: '/blog/post-name' within a page component—cannot mathematically resolve to an absolute string.7 Because the Next.js build environment operates without knowledge of the final deployment domain context, Next.js 15 and 16 will either trigger a terminal build error or output a critically invalid relative canonical tag directly into the Document Object Model (DOM).5 Google Webmaster Guidelines strictly mandate the use of absolute paths for canonical tags; relative paths are highly susceptible to parsing errors, infinite loop generation, and cross-domain dilution.5 If Googlebot encounters a relative canonical tag, the algorithm frequently ignores the directive entirely. This failure results in severe duplicate content penalties and triggers the "Crawled - currently not indexed" status, as the engine struggles to determine which URL variant constitutes the authoritative document.5
Beyond canonicalization, the omission of metadataBase catastrophically breaks the Open Graph (OG) protocol.7 Social media platforms and Google Discover rely on absolute URLs to fetch preview images.7 A relative image path defined in the metadata object will fail to render, degrading click-through rates and reducing the perceived quality of the page in the eyes of search algorithms.7
To definitively rectify this architectural flaw, the metadataBase must be explicitly instantiated in the root layout.tsx file using the native JavaScript new URL() constructor, pointing directly to the absolute production domain.7 Subsequently, every dynamically generated page must utilize a robust metadata builder function that constructs explicit, absolute canonical paths that seamlessly and perfectly align with the URLs broadcast in the XML sitemap.7

Advanced Dynamic Sitemap Generation and Caching Semantics
The Extensible Markup Language (XML) sitemap serves as the definitive, machine-readable roadmap for search engine crawlers, aggressively highlighting the application's most critical canonical URLs, their precise modification timestamps, and priority hierarchies.7 Rather than forcing Googlebot to rely entirely on organic link-following—which can lead to deep, orphaned pages remaining undiscovered—a technically flawless sitemap proactively injects canonical pages directly into the crawling queue.7
In Next.js 15 and 16, sitemap generation is natively handled via the sitemap.ts file convention, functioning as a specialized Route Handler within the App Router.20 A critical breaking change introduced in the Next.js 15 transition significantly altered the routing behavior for programmatic sitemaps: dynamic sitemaps defined via .ts or .js extensions no longer serve at the traditional /sitemap.xml endpoint by default. Instead, they resolve natively at /sitemap or /sitemap/[id] when utilizing the generateSitemaps() API for massive multi-sitemap architectures.21 While Next.js handles the content type headers correctly, engineers must ensure that their robots.txt explicitly points to this newly formatted URL structure.
To completely eliminate "Discovered - currently not indexed" discrepancies, the dynamically generated sitemap must output absolute URLs that perfectly match both the next.config.js trailing slash rules and the layout's canonical structures.7 If a URL declared in the sitemap differs from the canonical tag injected on the actual page by even a single trailing slash, Googlebot views the discrepancy as conflicting signals. This forces the indexing algorithm to reconcile the conflict, plunging the URL into an indexing delay while it attempts to determine the true canonical.22 Updating the sitemap to perfectly mirror the canonical output instantly resolves these reconciliation delays.22
Furthermore, the sitemap.ts file must dynamically fetch backend routing data to ensure newly created pages are instantly broadcast to search engines upon publication. The lastModified XML payload is actively extracted and evaluated by Googlebot to determine crawl frequency optimization; presenting an inaccurate or perpetually static timestamp causes the crawler to fundamentally distrust the sitemap, leading it to revert to slower, less efficient organic link discovery methodologies.23

import { MetadataRoute } from 'next';
import { getAllPosts, getAllServices } from '@/lib/api';

// Enforce strict caching semantics. Revalidate the sitemap payload every 24 hours 
// to prevent database overload while ensuring Googlebot receives fresh timestamps.
export const revalidate = 86400; 

export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
 const baseUrl = process.env.NEXT_PUBLIC_SITE_URL || 'https://www.endpointmedia.com';

 // 1. Fetch all dynamic content structures concurrently to minimize generation latency
 const [blogPosts, services] = await Promise.all();

 // 2. Map dynamic blog routes with precise timestamping
 const blogUrls: MetadataRoute.Sitemap = blogPosts.map((post) => ({
   // Strictly no trailing slash to align with next.config.js 
   url: `${baseUrl}/blog/${post.slug}`, 
   // Dynamically map to the exact publication or modification date 
   lastModified: new Date(post.updatedAt || post.createdAt),
   changeFrequency: 'monthly',
   priority: 0.7,
 }));

 // 3. Map dynamic service routes
 const serviceUrls: MetadataRoute.Sitemap = services.map((service) => ({
   url: `${baseUrl}/services/${service.slug}`,
   lastModified: new Date(service.updatedAt),
   changeFrequency: 'weekly',
   priority: 0.8,
 }));

 // 4. Define static architectural hub nodes [7, 20]
 const staticUrls: MetadataRoute.Sitemap =
     lastModified: blogPosts.length > 0? new Date(blogPosts.updatedAt) : new Date(),
     changeFrequency: 'weekly',
     priority: 0.9,
   },
   {
     url: `${baseUrl}/services`,
     lastModified: new Date(),
     changeFrequency: 'monthly',
     priority: 0.9,
   },
 ];

 // 5. Aggregate and return the unified sitemap object for XML generation
 return [...staticUrls,...serviceUrls,...blogUrls];
}

	React Server Components and Hydration Rendering Bottlenecks
The internal architecture of the React component tree directly dictates the success or catastrophic failure of the Googlebot rendering pipeline. The Next.js App Router defaults entirely to React Server Components (RSC), a paradigm shift that executes logic exclusively on the server (Node.js or Edge runtime) and streams strictly zero kilobytes of JavaScript payload to the client browser.1 This architecture is structurally pristine for SEO, as it guarantees that fully formed HTML is instantly available during Googlebot's primary crawl phase.1
However, enterprise development teams frequently override this default behavior by indiscriminately declaring the "use client" directive at the absolute apex of the component tree to quickly access browser-specific APIs (like window or localStorage) or to utilize interactive state management hooks (useState, useEffect).1 This architectural misstep instantly converts the entire downstream React tree into Client Components, triggering catastrophic SEO hydration delays.1
As previously established, Google's indexing system parses initial HTML before executing JavaScript.2 When "use client" is heavily utilized across core architectural layouts, the initial HTML payload sent to the crawler over the network is completely hollowed out.2 The server simply returns an empty JavaScript mounting point, completely masking the contextual content, headings, and internal links from the crawler's initial pass.2 Googlebot is forcefully shunted into the deferred rendering queue.2
During this deferred execution, the massive client-side JavaScript bundle must be downloaded, parsed, and executed to rebuild the DOM from scratch—a highly intensive process known as hydration.1 If the client bundle is excessively bloated with heavy layout components, the hydration process generates massive CPU spikes that lock the browser's main thread, resulting in a severe degradation of the Interaction to Next Paint (INP) metric.1 Googlebot operates on a highly strict rendering budget; if main thread hydration stalls or times out, the crawler algorithmically aborts the execution before the content becomes fully visible to the DOM.1
The affected URL is consequently flagged within Google Search Console as "Crawled - currently not indexed" because the crawler evaluated a broken, empty, or half-rendered DOM state, determining the page lacked sufficient quality for inclusion in the search index.1
To permanently resolve hydration bottlenecks, the application architecture must rigidly adhere to the Server Component paradigm for all SEO-critical data. Content-heavy nodes—such as article bodies, product descriptions, e-commerce pricing tables, and global navigational layouts—must remain strict React Server Components, generating fully populated HTML on the initial server request.1 Interactivity must be aggressively pushed to the absolute edge of the component tree, isolating client-side execution to "leaf nodes" that do not block the primary content render.1

Network Boundary Resolution: Proxying and Bot Detection
A hidden and highly destructive vector for massive "Discovered - currently not indexed" anomalies lies deeply embedded within the Next.js network interception layer. In the transition to the Next.js 16 Beta, the core development team officially deprecated the traditional middleware.ts file convention, replacing it entirely with the proxy.ts architecture.11 This renaming and architectural shift was implemented to clarify the module's role as a strict, low-level network boundary operating on the stable Node.js runtime, rather than functioning as a generic middleware chain executing on the volatile Edge runtime.27
Engineers frequently utilize this proxy network layer to enforce rigid authentication checkpoints, execute geolocation routing, or apply internationalization (i18n) localization rules.31 A standard, flawed implementation inspects the incoming request headers for active authorization tokens or pre-set language preference cookies; if these cookies are absent, the proxy forces an HTTP 307 Temporary Redirect or 308 Permanent Redirect, violently shunting the user to a default locale pathway or a login screen.31
Because search engine crawlers operate entirely statelessly—they do not process, store, or transmit cookies during their traversal of the web—Googlebot invariably fails these proxy cookie checks.31 Consequently, when Googlebot attempts to crawl deep architectural links mapped in the sitemap.ts, the proxy.ts intercepts every single request and hurls the bot into a relentless redirect loop back to the homepage or login portal.31 The application becomes completely opaque to the crawler, resulting in devastating indexing blockades.31
Furthermore, improper configuration of custom headers within the proxy layer can inadvertently inject X-Robots-Tag: noindex HTTP directives globally, explicitly forbidding the crawler from mapping the domain at the network level, entirely circumventing any positive <meta name="robots"> HTML tags rendered by the application components.3
To thoroughly resolve these network bottlenecks, the proxy.ts module must actively perform Adaptive Content Negotiation and algorithmic bot detection. By extracting and parsing the incoming User-Agent string from the request headers, the proxy engine can algorithmically identify crawler signatures (such as Googlebot or bingbot) and explicitly bypass the cookie-dependent redirect logic via the NextResponse.next() API.31 This grants the search engine crawler unfettered, direct access to the requested document without triggering redirect loops.

// proxy.ts (Located at the absolute project root, formally replacing middleware.ts)
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

// Define the comprehensive regular expression to accurately detect active search crawlers.
// This ensures that major search engines are never trapped in redirect loops.[31, 35]
const BOT_USER_AGENT_REGEX = /bot|crawler|spider|googlebot|bingbot|yandex|baiduspider|slurp/i;

export function proxy(request: NextRequest) {
 const { cookies, headers, nextUrl } = request;

 // 1. Extract the User-Agent string from the incoming HTTP request headers.
 const userAgent = headers.get('user-agent') || '';

 // 2. Evaluate the request against the bot signature regex.[31, 35]
 const isBot = BOT_USER_AGENT_REGEX.test(userAgent);

 // 3. Crawler Bypass & Header Sanitization Check
 if (isBot) {
   // Search engines are granted immediate, unimpeded passage without cookie validation.
   // This totally eliminates the "Discovered - currently not indexed" redirect traps.
   const response = NextResponse.next();
   
   // Explicitly enforce that the HTTP X-Robots-Tag is NOT restricting the bot.
   // This overrides any potentially inherited restrictive headers ('noindex') 
   // injected from upstream CDN or infrastructure layers.[34]
   response.headers.set('X-Robots-Tag', 'index, follow');
   
   return response;
 }

 // 4. Standard Application Logic for Human Traffic
 // Example: Enforcing internationalization (i18n) localization cookies for organic users.
 const localeCookie = cookies.get('NEXT_LOCALE')?.value;
 
 if (!localeCookie &&!nextUrl.pathname.startsWith('/en')) {
   // Human users without cookies are redirected to a default locale, 
   // while bots bypassed this block entirely to index the deep content.
   return NextResponse.redirect(new URL(`/en${nextUrl.pathname}`, request.url));
 }

 return NextResponse.next();
}

Pre-Deployment Algorithmic Validation Engine
To permanently eradicate "Discovered - currently not indexed" and "Crawled - currently not indexed" errors from the application lifecycle, technical SEO validation must shift left into the continuous integration (CI) pipeline or local development workflow. Relying entirely on the Google Search Console dashboard for error detection introduces a massive, unacceptable temporal lag; by the time GSC reports a canonical mismatch or a 308 redirect loop, the architectural damage has occurred, organic traffic has plummeted, and the domain's allocated crawl budget has been utterly wasted.
The optimal, enterprise-grade solution is a robust, asynchronous Python validation script that algorithmically mimics Googlebot's discovery and parsing phase.14 The engine must natively parse the locally hosted XML sitemap structure, extract every declared <loc> path, and execute HTTP GET requests against them simulating a crawler's User-Agent.38
Crucially, the script evaluates the response directly at the network layer to detect non-200 HTTP status codes, specifically targeting and flagging 308 Permanent Redirects caused by Next.js trailing slash discrepancies or flawed proxy.ts logic.36 By forcing the requests library to disable automatic redirect following (allow_redirects=False), the script catches the HTTP 308 response before it resolves, pinpointing the exact source of the crawl trap.
Following the network evaluation, the engine must parse the raw DOM utilizing the BeautifulSoup library configured with the rapid html.parser engine.38 It inspects the <head> block for malicious noindex directives and strictly compares the extracted <link rel="canonical"> href string against the requested URL.38 Any variance—even a single trailing slash discrepancy caused by a missing metadataBase—triggers an immediate failure alert. This allows the engineering team to resolve the canonical mismatch prior to production deployment, guaranteeing flawless indexing.14

#!/usr/bin/env python3
"""
Pre-Deployment Next.js SEO Validation Engine
Parses XML sitemaps, verifies HTTP network status codes, and mathematically validates canonical alignment.
"""

import urllib.request
import xml.etree.ElementTree as ET
import requests
from bs4 import BeautifulSoup
from urllib.parse import urlparse

# Define the target local or staging environment to crawl prior to production
SITEMAP_URL = "http://localhost:3000/sitemap.xml"

# Simulate Googlebot's exact signature to test proxy.ts bypass logic and content negotiation
HEADERS = {"User-Agent": "Mozilla/5.0 (compatible; Googlebot/2.1; +http://www.google.com/bot.html)"}

def fetch_sitemap_urls(sitemap_url):
   """
   Fetches the XML sitemap over the network and extracts all <loc> routing nodes.
   Accounts for standard sitemap XML namespaces to prevent parsing failures.
   """
   print(f"[*] Fetching sitemap payload: {sitemap_url}")
   try:
       request = urllib.request.Request(sitemap_url, headers=HEADERS)
       with urllib.request.urlopen(request) as response:
           xml_data = response.read()
           
       root = ET.fromstring(xml_data)
       # Define the strict XML namespace utilized by Next.js MetadataRoute APIs
       namespace = {"sm": "http://www.sitemaps.org/schemas/sitemap/0.9"}
       
       urls =
       for loc in root.findall(".//sm:loc", namespace):
           if loc.text:
               urls.append(loc.text.strip())
               
       # Fallback recursive search if strict namespace parsing fails
       if not urls:
           for loc in root.findall(".//{http://www.sitemaps.org/schemas/sitemap/0.9}loc"):
                if loc.text:
                    urls.append(loc.text.strip())
                    
       print(f"[+] Discovered {len(urls)} active URLs within the sitemap tree.")
       return urls
   except Exception as e:
       print(f"[!] Critical Network Error fetching sitemap: {e}")
       return

def validate_url(url):
   """
   Executes an HTTP GET request, verifies the network status code, and parses the DOM 
   for strict canonical alignment and meta robots tag sanitization using BeautifulSoup.
   """
   try:
       # allow_redirects=False is the most crucial parameter here. 
       # It forces the script to catch 308 loops natively before they resolve.[40]
       response = requests.get(url, headers=HEADERS, timeout=10, allow_redirects=False)
       status = response.status_code
       
       if status!= 200:
           print(f"[FAIL] {url} returned HTTP Status {status}. Check proxy.ts or trailing slash redirects.")
           return False

       # Evaluate network-level headers for invisible X-Robots-Tag blocking directives.[34]
       x_robots = response.headers.get("X-Robots-Tag", "").lower()
       if "noindex" in x_robots:
           print(f"[FAIL] {url} is critically blocked by an X-Robots-Tag HTTP network header.")
           return False

       # Initialize the HTML parser to evaluate the raw DOM payload 
       soup = BeautifulSoup(response.text, "html.parser")
       
       # 1. Evaluate <meta name="robots"> for accidental component-level blocks
       robots_meta = soup.find("meta", attrs={"name": "robots"})
       if robots_meta:
           content = robots_meta.get("content", "").lower()
           if "noindex" in content:
               print(f"[FAIL] {url} contains an invalid <meta name='robots' content='noindex'> tag.")
               return False

       # 2. Evaluate absolute Canonical resolution and mathematical alignment
       canonical_link = soup.find("link", rel="canonical")
       if not canonical_link:
           print(f"[FAIL] {url} is missing a canonical link entirely. Verify metadataBase in layout.tsx.")
           return False
           
       canonical_href = canonical_link.get("href", "")
       
       # Strip protocols (http/https) and subdomains (www) for a baseline structural path comparison
       parsed_req = urlparse(url)
       parsed_can = urlparse(canonical_href)
       
       req_path = f"{parsed_req.netloc.replace('www.', '')}{parsed_req.path}"
       can_path = f"{parsed_can.netloc.replace('www.', '')}{parsed_can.path}"
       
       if req_path!= can_path:
           print(f"[FAIL] Canonical Mismatch Detected on {url}")
           print(f"       Requested Payload: {req_path}")
           print(f"       Canonical Output:  {can_path} (Verify trailing slash rules and metadata parameters)")
           return False
           
       print(f" {url} exhibits pristine indexing architecture.")
       return True

   except requests.RequestException as e:
       print(f" Socket connection failed for {url}: {e}")
       return False

def main():
   print("=====================================================")
   print(" Next.js Technical SEO Pre-Deployment Validation Run")
   print("=====================================================")
   
   urls = fetch_sitemap_urls(SITEMAP_URL)
   if not urls:
       print("Validation sequence aborted: No URLs discovered in the sitemap.")
       return
       
   passed = 0
   failed = 0
   
   print("\n[*] Commencing DOM parsing and HTTP network validation sequence...\n")
   for url in urls:
       if validate_url(url):
           passed += 1
       else:
           failed += 1
           
   print("\n=====================================================")
   print(f" Validation Complete. PASS: {passed} | FAIL: {failed}")
   print("=====================================================")
   
   # If any architectural flaws are detected, fail the CI pipeline to prevent deployment
   if failed > 0:
       exit(1) 

if __name__ == "__main__":
   main()

Architectural Synthesis
The persistence of "Discovered - currently not indexed" and "Crawled - currently not indexed" errors within advanced Next.js environments is rarely a symptom of low content quality or domain authority. Rather, it is a direct algorithmic manifestation of deep structural discord between the complex routing logic of modern JavaScript frameworks and the rigid, budget-constrained crawling parameters utilized by Googlebot. Search engines demand absolute determinism from server architecture; any ambiguity in routing, rendering, or canonicalization forces the crawler to abandon the task.
By strictly enforcing absolute parity between the next.config.js routing logic and the dynamically generated XML sitemap.ts, the application architecture definitively eliminates the HTTP 308 redirect chains that aggressively cannibalize the crawler's allocated budget. Defining a rigorous, absolute metadataBase within the root layout ensures deterministic canonical mapping, preventing the equity dilution and indexing confusion caused by relative URL generation. Furthermore, reverting the application architecture to strict React Server Component paradigms completely bypasses the catastrophic hydration timeouts and main-thread interaction bottlenecks that plague the Web Rendering Service's deferred execution phase.
Finally, modernizing the network boundary via the transition from middleware to the node-based proxy.ts module guarantees that crawlers are granted unimpeded, cookie-free access to the deep DOM layer. Implementing this comprehensive technical blueprint systematically resolves framework-level SEO degradation, ensuring flawless synchronization between the Next.js App Router and the most demanding search engine indexing pipelines in the industry.
